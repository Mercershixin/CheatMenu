二、★ 本轮唯一「必须真机实测」才发现的问题：长文本被静默截断

2.1 公式：-c 是总上下文，会被 -np 均分

每槽上下文 = -c ÷ -np        ← 这才是【单条请求】真正能用的窗口

旧的启动参数是 -c 16384 -np 32，于是：

每槽上下文 = 16384 ÷ 32 = 512 token

2.2 而 system 提示词自己就吃掉 339 token（实测，不是估算）

用 llama-server 的 /tokenize 真分词器量：

system 提示词 = 1207 字符 / 1352 字节  ->  339 token
英文对照：180 字符 -> 41 token ；360 -> 81 ；585 -> 131   (约 4.4 字符/token)

⇒ 每槽 512 时，只剩 512 - 339 = 173 token 留给「输入 + 输出」

所以 615 字符的长段落必然被截断，而且是静默的 —— 服务端不报错， 客户端只看到一个半截译文：

配置615 字符长段落，实测返回结果
-np 32（每槽 512）finish_reason = length 被截断，客户端毫不知情
-np 16（每槽 1024）finish_reason = stop 正常

更糟的是客户端当时硬编码 max_tokens = 1024 —— 比每槽上下文还大， 服务端只能把它静默截到 512。

2.3 修法（两端一起改）

服务端
-np 32 → -np 16（每槽 512 → 1024）。
★ 显存实测 5847 MiB / 8192，与旧配置基本相同 —— 总上下文没变，只是切法变了。 所以「想加每槽上下文」几乎总是改 -np，不必加 -c。
客户端
探测 /props 拿真实每槽上下文，输出上限跟随它：
Trans.maxTok = math.max(128, math.min(512, ctx - 512))，请求用 Trans.maxTok or 512。
复核
改完 /props 回报 total_slots=16、n_ctx=1024，与预期一致。

2.4 顺带实测：客户端不需要自己攒批（这条给"要不要合批"的争论画了句号）

把同时请求数 K 从 1 加到 16，墙钟时间只从 199ms 涨到 1025ms（亚线性）：

K（同时请求数）124816
墙钟199ms241ms406ms655ms1025ms
单条 p50198ms240ms377ms630ms852ms
失败00000

K 翻 16 倍，墙钟只涨 5 倍 —— 说明服务端本来就是健康的连续批处理。 ⇒「客户端攒一批再发」不会让延迟变好，只会引入「一失败整批重来 → 二次翻译」的风险。

也顺手验了 AiNiee 式的编号 + <textarea> 批量合并：对齐率确实是满分 （4 条 → 4/4、8 条 → 8/8、12 条 → 12/12），但耗时按条数线性上涨（939ms / 1500ms / 2290ms）， 相比单条没有速度收益。

结论：维持「逐条请求、不做批量合并」。 这条老设计原本只是取舍，现在有了实测依据。

测量脚本：.workbuddy/build/bench_runner.py（自管启停 + 读 /props + K 扫描 + 批对齐）· 同一次运行确认 total_slots=16 / n_ctx=1024 · 长段落 615 字符 → finish=stop（不再截断）

显存：服务运行期间实测总计 5847 ~ 6806 MiB / 8192（桌面空载基线约 620 MiB）， 数值随"同时开着什么"浮动；与每槽 512 的旧配置相差不大。
