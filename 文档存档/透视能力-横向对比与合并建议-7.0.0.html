Roblox 客户端里，「能交互」本质上只由少数几个具体类承载。把它们枚举一遍， 就等于把所有可交互物枚举了一遍，跟物品叫「箱子」还是叫「Crate_03」完全无关。

实测缺口（源码逐行查过）

TouchTransmitter
整份源码只出现 1 次（:13379 综合扫描的统计计数），从来没有当成透视判据用过。 这是目前最大的漏网来源 —— 老式游戏的宝箱、地刺、传送门大量走 Touched 而不是 Prompt。
Seat / VehicleSeat
出现 0 次。所有可坐物件（载具、椅子、坐骑）完全不亮。
扫描范围
只用 WS:GetDescendants()（仅 Workspace）。提示若挂在 ReplicatedStorage 或 PlayerGui 里就扫不到。
分类表匹配
现有的 11 类关键词表（箱子 / 拾取物 / 道具 / 躲藏点 / 书籍 / 梯子 / 按钮 / 传送 / 座位 / 商店 / 检查点） 只能算「锦上添花的颜色」。结构判据才是底座，而底座少了 TouchTransmitter 一块砖。

但有 4 个真实上限，必须知道

  1. 实例必须真的下发到你客户端。 放在 ServerStorage / ServerScriptService 里的东西， 客户端内存里压根不存在 → 任何脚本都透视不到。
  2. 游戏开了流式加载（StreamingEnabled） 时，远处地图还没下发 → 拉「全图」也白搭。 这不是脚本问题，是引擎的复制策略。
  3. 别人背包里的东西看不到。 Roblox 不会把别人的 Backpack 复制给你， 只有他人物模型上（手上握着）的 Tool 可见。这是引擎限制。
  4. 纯服务端判定的交互（服务端自己用 GetPartsInPart / 距离比较来判定，客户端只有一个普通 Part） 没有任何组件可枚举 → 只能靠名字或形状猜。这正是 doorShaped()（竖直薄板判据）存在的意义。

结论

把 TouchTransmitter + Seat/VehicleSeat 补进判据、把扫描范围从 Workspace 扩到 game，就能做到「只要客户端能看到、且属于这 5 类载体之一，一个不漏」。 剩下的那 4 个上限是引擎层的，跟你写什么脚本无关。

合并方案

做一个 SYS.Index 类，一次扫描产出分类好的桶：

SYS.Index.refresh()   -- 单次 GetDescendants，按组件分桶
  ├─ prompts   = { ProximityPrompt ... }        （含所属物件引用）
  ├─ click     = { ClickDetector ... }
  ├─ touch     = { TouchTransmitter ... }       ← 新增，见 T1
  ├─ seats     = { Seat / VehicleSeat ... }     ← 新增，见 T2
  ├─ tools     = { Tool ... }
  ├─ humans    = { Humanoid ... }（区分玩家/非玩家）
  ├─ doors     = 门·危险·切割·假门（带危险等级标记）
  ├─ minigame  = 小游戏区域物件
  └─ loot      = 掉落物候选

所有 7 个功能改成读桶，不再自己扫。收益： ① 全量扫描次数从 8 次/秒级降到 1 次；② 判据表只维护一份（M5 顺带解决）； ③ 新增能力（比如 TouchTransmitter 透视）只要往桶里加一行，所有消费者自动受益。

M2「生物透视」并进「玩家透视」→ 合成一个「活物透视」三态

依据：代码里已经是这个语义了 —— 开生物透视会自动打开玩家透视：

UI.Switch(p,"🐾 生物透视 (所有活物全亮 · 敌对=红 / 中立=橙)","ESP_NPC",function(on)
    if on then SYS.T_.ESP=true end          -- ← 自己就把玩家透视一起开了
    if not on and not SYS.T_.ESP and ... then SYS.ClearESP() end
    if SYS.BtnRefs then for _,f in ipairs(SYS.BtnRefs) do P(f) end end  -- ← 还要手动刷上面那个开关的显示
end)

问题：两个开关语义重叠（都是「活物」），互锁逻辑互相判断，还要靠 SYS.BtnRefs 手动同步 UI 状态， 脆弱且难维护。

合并方案：一个「👁 活物透视」下拉三态：关闭 仅玩家 全部活物（含 NPC/怪物）， 颜色规则统一成一张表（自己 / 队友 / 敌人 / 幽灵 / 敌对生物 / 中立生物）。 把 ESPNameTag / ESPWeapon 的互锁判断从 4 处减到 1 处。

M3「小游戏区域透视」并进「物件透视」→ 成为第 12 类分类

依据：ESP_Mini 的判据（名字命中区域名 duck hunt / chisel / gauntlet / …） 本质就是 PickKinds 里的第 12 类关键词，却做成了独立开关，还独立占着一次全量扫描。

现状的体验割裂：用户开「🔍 物件透视」，小游戏里的按钮/靶子不会亮； 必须再去 MachineParty 页单独开一次。而 MachineParty 页还只有这一个透视开关，页面显得很单薄。

合并方案：往 PickKinds 加一类：

{ name="小游戏区域", color=Color3.fromRGB(0,200,255),
  kws = {"duck hunt","duckhunt","chisel","gauntlet","rightofway","blindout","crushhour",
         "bumpermadness","mppadhost","mpstation","machin"} }

由「物件透视」总闸统一驱动（和现在 ESPItem/ESP_Door 的做法完全一致）， MachineParty 页只留自动躲 / 自动触发两个开关。顺手省掉一次全量扫描。

M4「玩家名字」+「头顶武器标记」→ 合成一个「头顶标签」

依据：两者都是挂在头顶的 BillboardGui，共用同一个高度参数 ESPNameH、 同一个清理路径 SYS.ClearESP()，开关互锁判断散在 4 处 （:12531 / :12534 / :12540 / :12541），每处都在重复检查另外三个开关。

合并方案：一个「头顶标签」开关 + 两个勾选项（名字 / 武器标记）。 互锁判断收成一处，UI 行数从 4 行降到 2 行。

M5把重复的判据表抽成共享常量

这三对功能各自维护了一份内容几乎相同的判据：

重复对现状合并后
门/陷阱透视 ↔ 自动躲伤害机关源码自己写了「与「门/陷阱透视」同判据」共用 TRAPKW / KW 表
分类表「躲藏点」↔ 自动藏身各自写一份躲藏点判据共用一份「藏身点」判据
分类表「书籍/线索」↔ 读密码提示ReadHintTexts 里又写了一遍 hint/book/note/paper共用「线索物件」判据
小游戏区域表 ↔ 自动触发小游戏目标两边各有一份区域名数组共用 MINI_AREA（M3 会顺带合并）

M1 的索引器天然解决这件事 —— 判据只存在于索引器里，功能层只读结果。

——不建议合并的

  • 子弹射线（Tracer）：是「我打哪」的调试可视化，跟「地图上有什么」不是一回事，合并只会让语义变糊。
  • 光照档位 / 禁雾 / 禁阴影 / 随身灯笼：属于环境改造，和物件透视没有耦合关系，保持独立。
  • 自由视角（FreeCam）：是相机能力，不是透视。硬并进去会让「视觉页」变成杂物抽屉。
  • 透视距离滑条：不建议并进别的开关，但建议做成「物件透视」的展开子项 —— 现在物件透视全关时它还挂在界面上，容易让人以为在起作用（实际只作用于物件/门/小游戏）。
