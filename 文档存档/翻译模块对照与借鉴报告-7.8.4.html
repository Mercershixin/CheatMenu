一、结论摘要

你的翻译模块不是"一堆散装 bug"，而是三个架构层面的缺口在放大所有小毛病。

  1. 请求层没有"并发上限 + 合批" —— 开界面瞬间有多少条新文本，就有多少个并发 HTTP 打向本地 7B。P0-1
  2. 没有"动态文本"识别 —— CPS / 倒计时 / 金币这类每秒变的文本，每变一次 = 一次请求 + 一条缓存，永远停不下来。P0-2
  3. 失败容错是单向的 —— 我们有"退避"，但没有"到此为止"，也没有"哪条翻不了"的可见反馈。P2

XUnity 恰好在这三处各有成熟做法，而且可验证地写死在配置里（见第三节）。除此之外，本次还定位到一个可完整复现的真实功能 bug：开了「中英对照」之后，括号里的原文会被二次翻译吃掉 —— P1-3「金币 (Coins)」→「金币(金币)」，完整证据链在第四节。

二、为什么拿 XUnity.AutoTranslator 当基准

仓库
bbepis/XUnity.AutoTranslator（GitHub，本机 api.github.com 直连可读，本次实际拉取源码核对）
定位
游戏运行时 UI / 资源文本自动翻译框架，BepInEx / MelonLoader / UnityInjector 三套宿主
核心文件
SpamChecker.cs、TranslationManager.cs、Endpoints/TranslationEndpointManager.cs、Configuration/Settings.cs
为什么选它
它解决的是和我们一模一样的问题：一个持续变化的游戏界面里，"哪些文本该翻、多久翻一次、翻不出来怎么办、怎么不把翻译服务打爆"。它把这些问题拆成了独立组件并量化了阈值。

不适合直接照抄的部分先说清楚，省得后面白讨论：XUnity 是 Unity 插件的 C# 实现（有 Time.frameCount、组件级 Harmony 钩子、可以整插件 Shutdown），我们是 Roblox 执行器里的单文件 Lua（只有 os.clock()、属性变更信号、绝不可能"把用户的翻译功能关掉"）。所以下文只借机制，不借实现。

实际后果（可推演，非猜测）

界面翻译循环 :9842–9861 每 0.5 秒遍历一次 PlayerGui + CoreGui + gethui 的全部后代。一轮里若出现 200 条未缓存文本（换页面/开局都很正常），就会有 200 个协程同时落到 rawRequest，每个 Timeout=60（:9368）。本地 7B 服务通常只有 4–8 个并发槽 → 其余全部排队或超时。

我们的对应物只有一条，且只挡住最粗的那种

:9107–9110 的 ⑨ 号过滤：

-- CheatMenu-6.9.1.lua:9110
-- ⑨ ★★ 用户反馈「数字类文本一直被翻, 缓存疯涨」...
if not s:find("%a") then return false end   -- 纯数字/纯符号: 没有可翻的内容

它只挡"一个字母都没有"的文本。只要带一个字母就全线放行：

  • "Time left: 12s" → 有字母 → 放行 → 每秒一次请求 + 一条缓存
  • "CPS: 1234" → 放行 → 每秒一条
  • "Score: 1,234,567" → 放行 → 每变一次一条
  • "1.25K Coins"（:9016 还专门为这种做了本地词表）→ 数值变化后整串是新 key → 放行

换算一下：一条 "Score: N" 在 10 分钟里能产生 600 次 HTTP 请求和 600 条缓存条目，全部塞进 Cache 并每 2 秒被 saveNow() 整体 JSON 序列化一次（:9226–9245）。这同时解释了用户三个直观感受：越玩越卡、缓存条数一直在涨、模型槽位永远被占满。

注：RemindsOf 是纯字符串前缀/后缀比较，Lua 里用 s:sub(1,#o)==o 一类判断即可等价实现，零依赖、零额外 HTTP，属于"可以今天就加"的一类。

3.3 失败处理：他们有"上限"，我们只有"退避"

维度他们的我们的
单条文本失败 RegisterTranslationFailureFor 记失败次数；CanTranslate 里比对 MaxFailuresForSameTextPerEndpoint，超过就这条文本不再给这个端点。 :9176–9205 指数退避：3s→6→12→24→48→96→192→300 封顶（FAIL_BASE=3, FAIL_CAP=300）。没有次数上限 —— 300 秒后仍会无限重试。
失败回收 随端点健康度整体升降。 :9196–9202 超过 FAIL_MAXN=4000 条时，只清"冷却已过"的条目。做法正确。
端点/服务不可用 多端点 + InvokeJobFailedWithFallbaack：主端点失败自动切备用端点。 :9208–9215 全局闸门：连续 3 次传输失败 → 全体暂停 4 秒，自动恢复。只有单个本地服务，没有 fallback。
用户可见性 日志明确打出 SPAM DETECTED: ... 原因。 UI 只显示 命中 N | 本地 N | 失败 N | 跳过扫 N | 均 Nms（:13610–13621），看不到"哪条翻不了、为什么"。有 Trans.dumpPairs()（:10023）但只打印成功对照，失败侧是真空。

取舍判定：我们没有"次数上限"是刻意的 —— :9173 写着 ⚠️ 这是"退避", 不是"永久拉黑" —— "某些文本整局永不翻译"是另一个毛病, 绝不能引入。 这个判断我认为是对的、该保留。但缺一个折中："连续失败 N 次后，只在你手动重扫/清缓存时再试"，既不永久拉黑，也不再白白占槽位。这正是 XUnity 的 MaxFailuresForSameTextPerEndpoint 想做的事，只是我们不该学它"永久"，应该学它"封顶"。

4.1 P0-1 无并发上限 + 无合批 → 开界面时并发打爆本地服务

现象
开启界面翻译后开头十几秒明显卡顿/翻译成片超时；服务端日志瞬间涌入请求。
位置
:9481–9513 Trans.request（task.spawn 无闸）· :9425 rawRequest(...,1024) · :9368 Timeout=60
触发
任意一次扫描里出现 ≥ 本地服务槽位数（常见 4–8）的未缓存且互不相同的文本。
影响
请求排队 → 单条延迟从秒级涨到几十秒 → 用户看到"翻译不出来"；同时大量协程各挂 60 秒。
对照
XUnity：MaxConcurrency + MaxTranslationsPerRequest（见 3.1）。

4.2 P0-2 无动态文本识别 → 每秒变的文本永久刷请求 + 撑爆缓存

现象
越玩越卡；已缓存 N 条持续单向增长；本地模型槽位长期被同一批"数字文本"占满。
位置
:9095–9112 shouldTranslate（⑨ 只判 %a）· :9107 注释已记录过一次同类投诉
触发
文本含至少一个字母且每秒变化：CPS / 倒计时 / 分数 / 金币。
影响
每条变体 = 1 请求 + 1 缓存条目；saveNow 每 2 秒整体 JSON 序列化一次全表（:9230–9234），缓存越大尖峰越重。
对照
XUnity SpamChecker 五重检查 + RemindsOf（见 3.2）。

4.3 P1-3 【功能真 bug】中英对照自噬：金币 (Coins) → 金币(金币)

这是本次唯一一个可以完整逐行复现的功能性错误，而且只在我们自己的"中英对照"功能下出现。根因是混排翻译路径绕过了 alreadyOurs 自我保护。

① 用户开启 TransBilingual，biText（:9674–9678）产出 "金币 (Coins)"，writeProp 写入控件。
② 这个控件被我们挂过 GetPropertyChangedSignal("Text")（:9658）→ 我们自己的写入也触发监听 → onTextChanged → processLabel。
③ verdictOf("金币 (Coins)")（:9141–9152）：含汉字 → 走混排分支 → splitSegments 得 {"金币", " (Coins)"}。
④ 对非汉字段调用 Trans.shouldTranslate(" (Coins)")（:9146）—— 注意传入的是片段，不是整串，所以 alreadyOurs（:9097）检查的是 " (Coins)"，必然未命中 → 判定"有外文，要翻" → v.mixed=true。
⑤ Trans.processMixed（:9553–9604）把 " (Coins)" 当新文本 → 缓存未命中 → 真的发一次 HTTP → 模型返回 "(金币)"。
⑥ flush()（:9565–9585）执行 plainReplace("金币 (Coins)"," (Coins)","(金币)") → 写回 "金币(金币)"。
⑦ 第三轮："金币(金币)" 的非汉字段只剩 "(" ")"，#s<2 被挡 → v.skip → 收敛。终态 金币(金币)，原文已被吃掉。

为什么 alreadyOurs 没救回来：Trans.Outputs 里存的是整串输出 "金币 (Coins)"（:9530 markOutput(newText)），但混排路径是拿片段去查的。键的粒度不一致，保护网漏了。

同一根因的另一面：任何"译文里仍留英文"的输出（模型保留品牌名/专有名词，例如 "金币 Robux"）都会被这条路径重新扫一遍。对 "Robux" 这类本地词表里 hit==f 的条目（:9590 判 hit~=f 才用）会落进 Trans.request → 发一次注定失败的请求 → tidy 判"原样返回" → markFail。也就是每轮都在为空转的请求累积失败冷却。

影响面：仅在中英对照开启时可见，但一旦开启就是稳定复现、且方向是"越翻越错"。关掉对照则不出现。

4.4 P1-4 「翻译后发送」绕过冷却/闸门，且污染共享网络状态

现象
点了"发送"翻译失败几次之后，界面翻译会莫名停 4 秒。
位置
:9459–9477 Trans.translateTo · :9469 直接 rawRequest · :9211–9215 共享的 NetStreak/NetGateUntil
原因
两条路径的容错不对称：Trans.translate（:9422）会查 inCool/netGateOn，translateTo 两者都不查；而两者共用同一个 noteNetFail() 连败计数。
影响
① 发送方向没有退避，反复失败会反复打；② 它的失败会让界面翻译的全局闸门被误触发，两个独立功能的容错状态串了。

4.5 P2-5 质量门太弱 → 脏译文直接写进游戏 UI

-- CheatMenu-6.9.1.lua:9395
local function tidy(res,src)
    res=stripRich(res)
    res=(res:gsub("^%s+","")):gsub("%s+$","")
    if res=="" then return nil end
    if res==src and not hasChinese(src) then return nil end   -- 只挡"一模一样"
    return res
end

只挡"空"和"完全原样返回"。以下都会直接写进界面：

  • 模型加解释："Translation: 金币" / "翻译：金币" / "Here is the translation:" —— 无前缀剥离。
  • 模型截断/半截句 —— 无长度比校验（译文长度 > 源 3 倍或 < 源 1/3 都可疑）。
  • 只改大小写：源 "Coins" 回 "coins" —— res==src 不成立（大小写不同），判定通过并写回。
  • 模型复读多遍 —— 无重复检测。

对照：XUnity 侧有专门的译文校验层。这一条改动成本最低、用户可见度最高。

4.6 P2-6 掩码回填时可能漏出孤儿字符

:9346–9353 unmask：s:gsub("▮%s*(%d+)%s*▮", …) 容错一定空白，但若模型把 ▮7▮ 写成 7▮（丢了前哨兵），第一条匹配不上，第二条 gsub("▮[^▮]*▮","") 也匹配不上，最后只剩 gsub("▮","") 删掉哨兵 → 界面里留下一个孤立的数字 7。

概率不高（模型基本会保留哨兵），但 maskSpecials 有 19 条规则（:9321–9342），一次文本里可能同时出现多个占位符，重排风险随数量上升。

4.8 P2-8 超时口径不一致

翻译主路径
:9368 Timeout=60（注释说明是为 7B 慢响应留的，合理）
健康检查
:10040 Timeout=10
服务器探测
:10046 Timeout=10

三条用途不同的请求用两套口径。若服务地址不可达（防火墙 drop 而非 refuse），Trans.translate 要挂满 60 秒才会 noteNetFail() 一次，而闸门需要 3 次失败才生效 —— 意味着最坏 180 秒内没有任何保护。checkLocal 只给 10 秒，两者结论可能互相矛盾（UI 显示"🟢 在线"但实际翻译全超时）。

4.9 P3-9 失败侧完全没有可观测性

UI 只给 5 个聚合计数（:13610–13621），Trans.dumpPairs()（:10023）只打印成功对照。用户看到"某块文本一直没翻"，无法判断是 —— 被 shouldTranslate 挡了？被 vr.skip 跳了？在 Fail 冷却里？还是模型返回被 tidy 判废了？四种原因对外长得一模一样。这是"感觉一堆 bug"的心理来源之一。

4.10 P3-10 聊天接管的固有限制（记录，非必修）

:9916–9952 用覆盖赋值接管 TextChatService.OnIncomingMessage（Roblox 该回调是属性，只能覆盖，不能 Connect —— 这是平台限制，不是我们的错）。但 :9967 stopChatListener 会把属性恢复成我们启动时保存的 oldOnIncoming；若这期间有第三方脚本（另一个翻译脚本/聊天增强）也做了接管，我们会把它的覆盖掉。同理，我们自己的回调也会把第三方的顶掉 —— 顺序决定胜负，无法协商。顺带：scanChatOnce 只扫 PG/CoreGui（:9897），漏了 gethui()。

六、需要你点头才能做的（有行为改变）

① 跨文本合批（MaxTranslationsPerRequest 思路）

我们:9479 明确写着"不做跨文本合批避免行错位"、:13566 把合批开关当死开关删了 —— 说明当初踩过坑。合批能直接把请求数压到 1/N（这是本地 7B 提速最大的一招），但必须解决"数组下标对回"和"模型合并/拆分条目"两个问题。XUnity 的做法是严格按下标对回 + 端点声明一次最多几条 + 失败则关掉合批并重排。要不要动，你定。

② 单条失败封顶后"只在手动重扫时再试"

会改变现有语义（现在是 300 秒封顶后永远自动重试）。做了它，"整局翻不出来的文本"从"每 5 分钟白试一次"变成"彻底静默直到手动重扫"。好处：不再白占槽位、缓存不再被失败项污染。代价：用户得知道有"重扫"这个按钮存在。要不要动，你定。

③ 缓存淘汰策略（Cache 加容量上限 + LRU）

会改变缓存内容本身（老条目被淘汰 = 再次翻译时重新请求）。修完 P0-2 之后缓存增长速度会大幅下降，这条可能就不必要了 —— 建议先修 4.2 再评估。

七、不建议学的

  • 整插件 Shutdown。XUnity 检测到 spam 直接 Settings.IsShutdown = true 把翻译功能关掉。我们的用户是主动开了开关的执行器用户，静默关掉功能比翻得慢更糟。→ 学判定，不学处置。
  • 多端点 + 自动 fallback。我们是"本地 llama.cpp 单服务"，没有第二个端点。加 fallback 等于引入云 API 与密钥，超出当前架构。
  • Unity 组件钩子 / Time.frameCount。没有对应 API，用 os.clock() 的秒级近似即可，不必强求帧级精度。
  • 他们的模板化缓存键（{{A}}）。需要模型配合遵守模板语法，改造成本高于收益；我们只缺"数字变化归一"这一小块，用"剥掉纯数字/数值单位后再做 key"就能覆盖 4.2 的大部分收益。
