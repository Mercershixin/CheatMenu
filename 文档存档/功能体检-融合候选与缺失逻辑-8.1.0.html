一、「⏱️ 跳过动态文本」是什么意思

一句话：把「每帧都在变、翻译了立刻过期」的那类文本记住并跳过， 不再为它们发请求、写缓存。

典型受害者：金币数、CPS 计数、倒计时、血量条数字、 距离读数 —— 这些每帧都变，翻译结果拿到手就已经过期了。不开这个开关的话， 同一个控件会以扫描频率反复进入翻译队列，白烧请求和缓存。

它怎么判定"这是动态文本"（源码实测）

DYN_WIN  = 12   -- 计数窗口(秒)
DYN_HITS = 4    -- 窗口内变化 >= 4 次 -> 判为动态
DYN_LEN  = 60   -- 超过 60 字符的文本不参与判定
DYN_MAX  = 6000 -- 标记表上限, 超了整表清空
  1. 按控件分别记账：DynByObj[控件] = {last=上次文本, t=窗口起点, n=变化次数, keys={}}。
  2. 只在"变了"的时候计数：文本和上次一样就 return（静态标签每次扫描都会被看到，不能算变化）。
  3. 归一化：dynNorm = 转小写 + 所有数字串换成 # + 折空白。 所以 金币 1234 和 金币 1238 归一到同一个键 金币 # —— 这正是"数字在变、文字没变"的识别方式。
  4. 12 秒内变满 4 次 → 把窗口内攒下的所有归一化键全部标记进 Trans.Dyn，计数 Trans.Stats.dyn +1。
  5. 落字前拦一道：shouldTranslate() 里 if dynIsBlocked(s) then return false end。

零成本快通道：if Trans.DynN == 0 then return false end —— 什么都没标记过的时候，判定是一个整数比较，不产生任何开销。

和「绝不永久拉黑」那条铁律冲突吗？

不冲突，源码注释也写明了：跳过的是"翻了也立刻过期"的文本，而且这份标记表是可清空的 —— 「🧹 清空缓存」和「🔍 立即强制全屏扫描翻译」都会把 Trans.Dyn 一起清掉， 用户随时能让它们重新试一次。
另外「🧹 查看已跳过的动态文本」按钮（Trans.dumpDyn()）会把当前被判定为动态的文本打到控制台， 可以随时复查它判得对不对。

二、哪些功能可以融合整合（5 个候选，按价值排序）

M1 · 玩家页 5 个「跟随」开关 → 一个互斥下拉 最该做

现状：循环跟传 · 坐他头上 · 绕着他旋转 · 盯着他 · 行走跟随 是 5 个独立开关，可以同时打开。

后果不是"不好看"，是行为打架：这几个功能都在写你的 CFrame。 本仓库自己有一条铁律 ——「同一时刻只允许一个模块写 CFrame；排查抖动/瞬移先问一句：现在有几个模块在写位置？」 所以 5 个同开 = 自己人打自己人 = 抖动/瞬移。

融合方案：一个「跟随模式」下拉（关闭 / 循环跟传 / 坐头上 / 环绕 / 盯着看 / 行走跟随）+ 保留 「旋转速度 / 环绕距离」两个参数。互斥由控件保证，从结构上消灭这一类 bug。

M2 · 视觉页「光照」区 4 个控件 → 一个档位 + 自定义

现状：🚫 禁雾、🌑 禁阴影、🏮 随身灯笼 三个独立开关， 加上一个 光照档位 下拉（关闭 / 夜视 / 超级光明 / 全亮）。

语义本来就重叠：看提示文本就知道 ——「全亮＝亮 + 正午 + 禁雾 + 禁阴影」。 也就是说「全亮」这个档位和那两个开关在做同一件事，用户会困惑"我选了全亮，那禁雾开关还要不要点"。

融合方案：档位扩成「关闭 / 夜视 / 超级光明 / 全亮 / 自定义」， 选「自定义」时才露出禁雾 / 禁阴影 / 灯笼三个细项（现在是常驻显示，所以看起来"重复"）。

M3 · 挂机页 7 个开关 → 「🛌 一键挂机」总闸

现状：挂机防踢、自动训练踢击力量、自动重生、自动领取训练加成、 优先参加健身事件、自动售卖、启用 CPS 门槛 各自独立。

融合方案：沿用本仓库已有的两种成功形态 （「🛡 一键开启全部防护」和「⚡ 一键开战 / 🛑 一键停战」）—— 加一个总闸按钮一键开齐常用组合，细项全部保留。 这是纯加法，不动任何既有开关的语义，风险最低。

M4 · 「自动交互」3 项 → 一个总闸

现状散在两页：视觉页的 ⚡ 快速交互、🏃 自动藏身， MachineParty 页的 🎯 自动触发小游戏目标、🏃 自动躲伤害机关。 它们的数据源是同一个（SYS.Index() 的统一扫描结果），语义都是"看到可交互/有危险就自动动手"。 → 可收成一个「⚡ 自动交互」分节 + 一个总闸。

M5 · 战斗页「选人规则」6 个开关 → 规则预设 建议缓

现状：360 无死角、只打指定目标、只锁活人、 不打队友、只打视野内、跳过无敌盾 都在「🧭 打谁 · 选人规则」这一分节里， SYS.T_ 实测它们本来就成组出现在同一个判断里（CB_360 + CB_Wall、 CB_360 + CB_Aim 等）。 → 理论上可做成「选人规则：宽松 / 标准 / 严格 / 自定义」。
⚠ 但这是战斗判据，动一下就是手感变化（本仓库的口径：战斗模块只允许"结构重排 + 状态私有化，判据逐条保留"）。 所以登记为候选，不建议现在做。

已经融合过的，不要重复劳动： 「玩家透视 + 生物透视」→ 活物透视三态 ·「名字 + 武器标记」→ 头顶标签 · 「掉落物 / 可交互 / 门·陷阱·假门 / 小游戏」→ 🔍 物件透视总闸 · 8 处各自的全量扫描 → SYS.Index() 统一索引器 · 重复判据表 → SYS.Kw* · 4 处互锁判断 → SYS.ESPAnyOn() / ESPMaybeClear()。 （见 AGENTS.md §2-D）

C5 · 一处轻微不一致（非 bug，但值得知道）

FreeCam（自由视角开关）在声明表里功能代码读 0 次 —— 但这不是 bug： 它走的是"回调型开关"（UI.Switch(...,"FreeCam",function(on) on and SYS.StartFreeCam() or SYS.StopFreeCam() end)）， 真正的运行态在 SYS.FreeCamActive。
⚠ 副作用：这个声明键只用来"记住开关位置"，重载脚本后开关会显示"开着"，但自由视角并没有真的启动 （同理的还有几个回调型开关）。若在意，可加一条"重载时按配置自动启动"的迁移。

四、必须更正的一件事：审计脚本自己的误报

我第一版体检脚本的 F 段报出「7 个界面引用的成员在正文里找不到实现」 （SYS.SetNoAggro / SYS.Lab / SYS.ApplyUIScale 等），看起来像 7 个"按钮点了会崩"。
逐个 grep 后 7 个全部有定义 —— 全是误报。原因是我的"剥掉页面区块"逻辑按 UI.Pages[...] 的行号切段，而实验室等模块物理上夹在两个页面定义之间，被一起遮掉了。
⇒ 这条结论已从报告里剔除。教训：用"剥块"做静态分析时，必须假设模块代码会落在块的缝隙里； 凡是要下结论，逐条 grep 复核（本次就是靠复核拦下来的）。
