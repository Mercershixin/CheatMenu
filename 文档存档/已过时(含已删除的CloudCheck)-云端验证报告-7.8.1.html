一、「云端」到底能测什么 —— 三条路线，只有一条能全自动

先把词说清，否则「测云端」会被理解成三种完全不同的事：

路线能给什么给不了什么本机能不能全自动
① 云端执行器
Lua 沙箱平台		 加载期/API 层的报错、环境能力探测结果 画面、描边、帧率 —— 没有渲染管线 不能 需要账号
② 云真机 / 云手机
真 Android + 真 Roblox		 唯一能给 G9（Highlight 配额）出数字的地方 不适合快速迭代（贵、慢） 不能 需要设备/账号
③ 分发链路验证
真网络 → 真 CDN → 真字节		 云端实际发给用户的是哪一份文件、能不能编译、字节是否与本地一致 不执行脚本（这是刻意的） 能 已自动跑完
④ 官方 Open Cloud
DataStore / 资产		 云端数据与资产发布 没有注入第三方 Lua 的入口，与验证脚本无关 不适用

为什么「③ 分发链路」值得当一等公民

这个项目里，用户手里只有 45 行加载器，其余全走网络。 所以「用户跑到的脚本」= CDN 那一刻返回的字节。这个字节对不对， 完全可以脱离执行器去验 —— 而且必须真拉，不能推理。 本机对 raw.githubusercontent.com 与 github.com 的连通性都不稳定， 所以「云端到底发什么」不是想当然的事，得实测。

二、全自动部分：分发链路验证（已完成）

怎么跑

python .workbuddy/build/cloud_verify.py            # 生产形态（带 ?t= 时间戳，与加载器完全一致）
python .workbuddy/build/cloud_verify.py --plain    # 对照：不带查询参数，用来区分「CDN 滞后」和「源真坏」
python .workbuddy/build/cloud_verify.py --quiet    # 只打结论块，适合塞进 CI / 门禁

退出码：0 = 至少一个源与本地逐字节一致且编译通过；2 = 没有任何可用源。 报告自动落盘到 dist/cloud/云端验证-<版本>-<时间戳>.txt。

它做四件事

  1. URL 从加载器里读，不是手写 —— 直接解析 dist/repo/loader.lua 的 URLS 表。 加载器改一条，测试自动跟着改，结构上不可能再对不上。
  2. 按生产形态真拉：加载器会拼 ?t=os.time() 穿缓存，测试也拼同样的。
  3. 与本地发行产物逐字节比对，并打印每个源的横幅版本（build … sha … bytes …）。
  4. 把「从云端拉下来的那份字节」直接送进 luau-compile。 这是关键差异：证明的是「云端发出去的东西能编译」，不是「我本地那份能编译」。

三、这一验，查出四件事

1. 测试脚本自己的 bug　URL 拼错，把活源误判成死源

第一版手写 URL 用了 "%s/%s/%s" % (SLUG, BR, BR)，而 SLUG 本身含斜杠 （Mercershixin/CheatMenu）→ 拼出 .../CheatMenu/main/main/CheatMenu.lua → 404。 于是 ghproxy / ghfast 这类明明活着的源被报成 BROKEN —— 差一点让我得出「云端全挂」的错误结论。

教训

凡是「测试脚本自己拼 URL」，就必须有单一真源兜着。 现在 URL 直接从 loader.lua 解析 —— 加载器是用户真正执行的那份，它才是事实。

2. 真问题　jsDelivr 会「静默」把旧版脚本喂给用户

同一时刻的实测（这是最直接的证据）：

jsDelivr 边缘它的 version.txt它的 CheatMenu.lua
gcore.jsdelivr.net7.8.1（最新）横幅 10:59 = 旧版
fastly.jsdelivr.net还是 7.8.0横幅 11:26 = 旧版

也就是说：用户问「有没有新版」得到「有（7.8.1）」，然后下下来的却是旧脚本。 这正是加载器注释里写了很多年的那句「更新不了 / 还是旧版」的真身。 根因是 jsDelivr 对分支名 @main 用的是文件级长缓存， 而且三个边缘节点各自停在不同旧版本。

顺带否掉一个流传已久的假设

加载器里那个 ?t= 时间戳参数，注释一直写着「CDN 会把 query 算进缓存键 → 每次都是新内容」。 实测对 jsDelivr 无效 —— 带与不带 query 返回的是同一份旧字节。 它对 raw 系有效（raw 原生缓存只有约 5 分钟）。所以救 jsDelivr 不能靠参数，只能靠排序。

3. 已修　源顺序改成「新鲜优先」

顺序本身就直接决定用户拿到新版还是旧版。改后（publish.py: raw_urls()，加载器与脚本内嵌候选同步）：

  • 第一梯队（新鲜，raw 系约 5 分钟刷新）： ghfast.top → ghproxy.net → raw → gh-proxy.com → ghpxy.hwinzniej.top
  • 第二梯队（命中可能静默给旧版）：jsDelivr 三节点 降为兜底
  • 第三梯队：githack / gitmirror（实测已死，留最后）

效果：前面任何一家活着，用户就轮不到那个会发旧版的 CDN。

4. 已堵　顺手堵掉一个「改顺序时自己埋的坑」

{{CM_URL}} / {{CM_VERURL}} / {{CM_REPO}} 原先都取 urls[0]。 源顺序一改，urls[0] 就从 raw 变成了代理地址 —— 而脚本的启动自更新检查是用 ^https://raw%.githubusercontent%.com/ 锚定解析用户/仓库/分支的；填代理地址进去会匹配失败， 自更新会悄悄退化成单源直连（代理一挂就再无兜底）。

已新增 canonical_raw() 专供这三个占位符：永远填 raw 规范地址，与下载源顺序彻底解耦。 产物里已核实：三个值都是 raw 规范地址，且 ghfast.top 作为候选源正常内嵌。

云端执行器拿不到什么

它只跑 Lua 沙箱，没有 Roblox 渲染管线。画面是否正常、ESP 有没有真的描边、 菜单在手机上点不点得到、帧率掉不掉、Highlight 有没有被引擎回收 —— 这里全看不到。 不要用它的结果推断画面表现。

B · 云真机：唯一能给 G9（Highlight 配额）出数字的地方

为什么 G9 只能在这里测

Highlight 的配额与回收发生在 Roblox 客户端的渲染与实例管理层，不在 Lua 沙箱里。 云端执行器里 Instance.new("Highlight") 只是建了个对象、从不进渲染路径，数出来是假象； 而且「人多」这个前提要求同一局真有大量角色，云端执行器通常跑空场景 —— 更假。

1

场景：云真机（Android + Roblox + 执行器），进人多的公共服，同屏 ≥10 个角色。 脚本用 7.8.1，开玩家透视（每目标一个 Highlight）。

2

测三条：① 实际带 Highlight 的角色数 == 看到描边的角色数？ ② 人数继续涨（或持续 60 秒）后，早期目标的描边会不会突然消失？ ③ 从 1 人 → 10 人 → 20 人，帧率怎么掉。

3

计数小抄（Highlight 挂在角色身上，h.Parent = 角色，不是固定容器）：

local n,t=0,0
for _,pl in ipairs(game:GetService("Players"):GetPlayers()) do
    local c=pl.Character
    if c then
        t=t+1
        if c:FindFirstChildOfClass("Highlight") then n=n+1 end
    end
end
print(("Highlight=%d / 角色=%d"):format(n,t))

3 秒平均帧率：

local f=0
local c=game:GetService("RunService").RenderStepped:Connect(function() f=f+1 end)
task.wait(3) c:Disconnect()
print(("FPS=%.1f"):format(f/3))

建议在 1 人 / 10 人 / 20 人三个时刻各跑一次这两段，把数字发我 —— 这就是 G9 要的量化。

五、门禁与边界（如实说明）

本轮门禁

  • 等价性 PASS　luau-compile 0 错误　加载器探针 6 通过 / 0 失败　加载器编译 通过
  • 静态接线检查 check.py：4 项，与 7.8.0 基线完全相同（都是历史遗留），本轮 0 新增。
  • 推送后回读：4 件套（CheatMenu.lua / version.txt / loader.lua / CHANGELOG.md）远端逐字节一致。
  • 云端链路：5 个源 IDENTICAL + 云端字节编译 OK；版本对齐 7.8.1。

残留风险（我知道但没瞒着）

  • gitmirror / githack 仍留在源列表里（实测本机连不上）。保留只为「多一个机会」，已排到最末。
  • jsDelivr 仍会在兜底位被使用。它可能给旧版 —— 但只有在前 5 个源全部失败时才会走到那里。
  • 本机连通性本身是变量：raw 上一轮超时、这一轮成功，说明它「抖」而不是「死」。 所以报告里区分了 BROKEN（当下不通）与 STALE（通但内容旧），不把二者混为一谈。
  • 分发链路验证不执行脚本 —— 这是刻意的设计边界，它替代不了路线 ① / ②。

仍然不做的事

按用户要求：整脚本仿真测试 / 循环检测彻底禁用，没有例外。 允许的验证只有三类 —— ① 静态分析 ② 单元测试 ③ 云端执行（OCALE）。 本报告做的是 ③ 里可以脱离执行器全自动完成的那一半。
