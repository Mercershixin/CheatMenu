二、怎么跑（就这一条）

python .workbuddy/build/cloud_verify.py            # 生产形态（带 ?t= 时间戳，与加载器完全一致）
python .workbuddy/build/cloud_verify.py --plain    # 对照：不带查询参数，用来区分「CDN 滞后」和「源真坏」
python .workbuddy/build/cloud_verify.py --quiet    # 只打结论块，适合塞进门禁

退出码：0 = 至少一个源与本地逐字节一致且编译通过；2 = 没有任何可用源。 报告自动落盘到 dist/cloud/云端验证-<版本>-<时间戳>.txt。

它做四件事

  1. URL 从加载器里读，不是手写 —— 直接解析 dist/repo/loader.lua 的 URLS 表。 加载器改一条，测试自动跟着改，结构上不可能再对不上。
  2. 按生产形态真拉：加载器会拼 ?t=os.time() 穿缓存，测试拼的完全一样。
  3. 与本地发行产物逐字节比对，并抠出各源的版本横幅（build … sha … bytes …）打进报告。
  4. 把「从云端拉下来的那份字节」直接送进 luau-compile。 这是关键差异：证明的是「云端发出去的东西能编译」，不是「我本地那份能编译」。

为什么 jsDelivr 显示 STALE 却不算失败

jsDelivr 对分支名 @main 用的是文件级长缓存： 同一时刻它的 version.txt 已经报 7.8.2，CheatMenu.lua 却还停在几小时前。 命中它就会静默把旧脚本喂给用户。7.8.1 起已把它从源列表第 2~4 位降到兜底 （顺序改成「新鲜优先」：raw 系在前）。所以它现在只是「兜底时才可能用到」， 不是失败，是设计上把它边缘化了。另外实测确认：加载器那个 ?t= 参数对 jsDelivr 无效，救不了它，只能靠排序。
