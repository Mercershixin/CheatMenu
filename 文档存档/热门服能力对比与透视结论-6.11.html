1 · git 同步结果

本地仓库位置：dist/repo/.git（注意：工作区根目录 不是 git 仓库）。

同步前：本地 HEAD 停在 d20b6ab（09-18 事件提交），落后远程 60+ 个提交；dist/repo/事件库/ 只有 4 个旧文件。

同步动作：fetch 镜像 → reset --hard FETCH_HEAD（镜像走 ghfast.top，因为本机 git 直连 github 会被重置）。

同步后：HEAD = 远程最新 4141f63；事件库/ 补齐到 9 个文件；工作区干净（仅余一个与远程无关的本地 .gitattributes）。

本轮复核：再次 fetch，HEAD..FETCH_HEAD 为空 ⇒ 远程无新提交，确实是最新。

校验方法：对根目录 9 个事件文件 + 4 个规范文件逐字节 sha1 比对 → 全部「一致」。

踩坑记录（值得记住）：一开始用 git hash-object 去和 sha1sum 对比，结果全部误报「有差异」。 原因：git hash-object 算的是 git blob sha（会把 blob <size>\0 前缀算进去），而 sha1sum 是纯字节 sha —— 两种算法，任何文件都比不平。判「两个文件是否相同」必须用同一种算法（本次改用 Python hashlib 逐字节）。

3 ·「无仇恨」机制核查

位置：CheatMenu-6.9.1.lua:12335-12447（UI 开关 :12443；诊断 SYS.NoAggroInfo）

它到底做了什么

核心 = 「甩仇」（用户澄清过：「让怪物和他打，相当于怪物和所有人打，除了我」）。
怪的仇恨 AI 跑在服务端，客户端唯一能插手的两条路：

  1. 改写目标字段（首选）：若怪把「当前目标」存在客户端可写字段里 —— Humanoid.Target 或 Attribute Target/Enemy/Aggro/TargetPlayer/TargetEntity/Hostile（:12365）—— 且当前指向你， 就改写成「离它最近的别的玩家」（otherTarget() :12352）。它于是转头去打别人。
  2. 改不动 → 退化：隐去自己 + 免伤 + 自动躲（它找不到你，只能去找别人）。

执行节奏：每 0.5s 扫一遍 Workspace 直接子对象的非玩家 Humanoid（NoAggroTick :12366），成本很低。

6.10.9 的关键修复（你踩过的坑）

症状：开了「无仇恨」就上下瞬移。
根因 1：旧版无仇恨强绑「三件套」，其中一件是藏地下隐身——每 1/30s 把你按到地下 120 格， 而位置是服务端权威的，服务端每帧把你拉回地面 ⇒ 客户端压下、服务端拉回 = 疯狂弹跳。
修法：无仇恨现在只挂 反陷阱免伤 + 自动躲（这两项不写位置），不再自动开藏地下隐身；关闭时也只还原它自己开的两项。
根因 2：AutoDodge 的退开方向用了 3D 向量，陷阱在地板/压板上时方向朝上 → 把你往上推。 现在压平到水平面（:5113）。
→ 通用教训：排查「抖动/瞬移」先问一句「现在有几个模块在写位置？」——大概率是自己人打自己人。
能力边界（必须说清）：怪物「恨不恨你」由服务端 AI 决定，客户端改不了。 所以「① 客户端存在可写目标字段」才有真正的甩仇效果；否则只能退化成隐身/免伤/躲——这是极限，不是脚本不行。

6 · 事件监听机制与内部逻辑

本脚本的「事件监听」是三套东西叠起来的，搞清楚这个就懂它为什么换游戏还能用。

① EventWatch —— 被动监听 + HUD 播报（:2359-2427）

  • 原理：Remote 的名字通常就写明用途。扫 ReplicatedStorage（优先 Remote 子夹）的全部后代，名字命中关键词表 :2360-2369 的才要。
  • 关键词表：monster/fake/real/boss/wave/round/event/spawn/alert/warn/announce/hint/notice + 从事件库抓包抄来的 touchdamage/querylock/selectrole/mailbox/roulette/battlepass/serverlist…（C5 扩展）。
  • 动作：给命中的 remote 连 OnClientEvent（:2404），一有动静就把参数前 3 个拼成文本，HUD 播报 📣 名字 → 值；同一 key 8 秒去重。
  • 诚实边界：能不能预告取决于游戏发不发信号；有些事件纯本地演，那就没有 remote 可听。

② SYS.FindEvent —— 主动查找 + 触发（:1005 起）

  • 14 个类别名表（claim / pickup / respawn / buy / teleport …），每类一串别名；
  • 别名没命中就关键词模糊扫描 ReplicatedStorage；
  • 调用侧先把所有候选排上（FindEvent 只返回第一个命中的），逐个试 —— 这是换游戏仍能生效的关键（不硬编码路径）。

③ T() / SYS.Conns —— 连接统一登记回收

所有 :Connect 经 T() 登记进 SYS.Conns，卸载时统一断开；「只挂一次」用弱表 setmetatable({},{__mode="k"})。 —— 这解决的是「反复开关菜单导致回调越积越多」的老问题。
与公开技术的对照：DevForum 那条 2026-09 的热门做法是 hookmetamethod(game,"__namecall", …) + getcallingscript() 伪造 RunService:IsStudio。 我们的 :11103 注释明确放弃在 __namecall（所有实例方法的总入口）上挂钩 —— 因为实测「极度卡顿掉帧」， 改成只 hook Player.Kick/Destroy 这两个具体目标。结论：监听面越窄越稳。

8 · 结论：截图这本书支持高亮透视吗？

✅ 支持 —— 会被「🔍 物件透视」点亮。

截图里那本书带 ProximityPrompt（屏幕上的 E 提示），这正好命中我们可交互透视的结构判定（第一优先）， 因此必定被画上高亮边框（按统一配色 = 亮青描边）。
说明：截图里那圈橙色框是游戏自己的选中高亮；脚本加上去的会是青色边框。

为什么必中（三条独立判据，命中任意一条即亮）

判据代码位置对这本书是否成立
① 结构判定（最硬） :4346-4367：扫 Workspace:GetDescendants()，任意 BasePart/Model/Folder 只要自己 / 父级 / 子级带 ClickDetector 或 ProximityPrompt 就命中。类名已从早期的 4 种放宽到任意 BasePart（:4350-4353）。 成立 有 E 提示 = 有 ProximityPrompt。
② 名字 / 祖先名分类 PickKinds 表 :4264-4314，其中「书籍/纸张/线索」关键词 :4289-4295：book / bookshelf / shelf / journal / note / paper / page / hint / clue / code / password / library … 及中文「书 / 笔记 / 纸 / 页 / 线索 / 密码 / 提示」。按名字 + 最多 3 层祖先名判（:4374-4382）。 大概率成立 书柜里的书通常名字含 Book，或祖先名含 Bookshelf/Library。
③ 结构兜底「能读的东西」 :4383-4395：名字再乱（Book1 / Part / Page），只要部件挂了 SurfaceGui 且里面有 TextLabel/TextBox，就判为「文字线索」点亮。 视情况 若书封面上有文字 UI，则必中。

什么情况下会「不亮」（边界，先说清）

  • 超出绘制距离：默认 PickDist = 1200 格（:4344、:4407），超了不画。可调大。
  • 还没复制到客户端：抽屉/书柜里由服务端按需下发的实例，客户端实例树里根本不存在 → 画不出来（这是引擎限制，不是脚本问题）。
  • 总开关没开：需开启「🔍 物件透视」（ESP_Pick，:4335）。
顺带一个细节：若书是 Model，脚本会把模型内部所有 BasePart 都点亮（每个模型上限 12 个，:4413-4423）—— 所以不会出现「只亮书脊一角」的尴尬（这正是 6.10.6 修的「书柜上的密码书看不见高亮」）。
