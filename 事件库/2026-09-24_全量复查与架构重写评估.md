## 一、先给结论（重要，和你预期可能不同）

**「死代码 / 断线开关 / 重复定义」这三类你担心的问题，实测是干净的：**

| 规模 | **19040 行 / 835735 B** 单文件 | — |
| `T_` 开关 | **108** 个 | — |
| `C_` 配置 | **70** 个 | — |
| `SYS.*` 函数定义 | **192** 处 | — |
| **重复定义**（同名函数定义 >1 次） | **0** | ✅ 干净 |
| **`T_` 死键**（全文引用 ≤1 = 只有默认值那行） | **0** | ✅ 干净 |
| **`C_` 死键** | **0** | ✅ 干净 |

⇒ **108 个开关里没有一个是"只定义了没人用"的**（每个至少被读一次）。
⇒ 所以「功能没接线 / 开关是死的 / 一堆重复函数」这个判断**不成立** —— 不要基于这个前提去重写。

## 二、那"乱"到底乱在哪？（4 条，都有证据）

1. **单文件 19040 行 + 12 层扫描混在一个 chunk 里**
   `T_`/`C_` 在 76~234 行，UI 定义在 11300~17500 行，运动核心在 1300 行，防回退在 1750 行，
   新模块块在 18400 行 —— **相关性靠"行号"而不是"模块边界"维系**。
   改一处要跳 5 个地方，这就是"错乱感"的真正来源。
2. **2 天内叠了 7 个版本**（11.3.0 → 11.5.1），其中 11.4.0 一次性塞进 A~L **60 项**新功能。
   每一版都是"锚点补丁 + 追加一段 `do ... end`" ⇒ **历史上多套实现并存**（本期已清掉一批：
   `FlyBV/FlyGyro/SpeedBV/SpeedGyro/SpeedLV/SpeedAtt/_FlyDegraded/gravZero/lastSM`）。
3. **同一概念曾经住两个模块**（移动 vs 过检测）—— 已在 **11.5.0 拆分定案**（`SYS._Move` + 独立 `SYS.AntiRevert`）。
4. **"每游戏专用模块"平行堆叠**：DeadRails（`SYS.DRHp`/`SYS.DRCombat`）、MachineParty、DOORS、FFA、
   Trans（翻译 4 层）、`SYS.AC`（D1~D14）、`SYS.Prot`（反指纹）—— 各自有独立状态与开关，**没有统一接口**。

## 三、为什么"全部重新写"是**现在最危险**的选择

1. **不可验证**。项目铁律禁整脚本仿真，只允许「静态分析 + 单测 + 云端分发链路」——
   **没有一样能证明"重写后功能还好用"**。19k 行重写后只能在真机里撞错误。
2. **会丢掉"只存在于这些行里"的知识**。100 多个版本换来的东西大多**不在文档里**，而是嵌在代码里
   （例：`AntiFling` 的 80 不能写死、`UI.Slider` 的 `get()` 必须落在 `[min,max]`、
   `EntityName=Horse` 是坐骑不能标红、GUI 必须挂 `PlayerGui` 否则偏 58px…）。文档里没写全，**重写必丢**。
3. **最近三次事故全都是"改架构"引起的**（11.4.0 A~L 大改 ⇒ 定在原地；11.4.1 调参救 ⇒ 拆掉过检测；
   11.5.0 重写 ⇒ 滑块夹到 16）。**大改的代价已经有实证，而且很大。**

## 四、推荐方案：**分阶段重构**（可验证、随时可停、每阶段都能发版）

### 目标架构（每层只做一件事，层间只走显式接口）
```
[0] 内核层      SYS.P / T / TT / SetLoop / SpawnLoop / SafeHook / SafeUnhook / Notify / GC / Orig / N / GK / GV
[1] 配置层      T_（开关，108） / C_（数值，70） / SaveConfig / LoadConfig / REMOVED_FEATURES / 迁移
[2] 通信层      REvent / REventU / RFunction / Fire / OnRemote / FindEvent / RemoteAlias / RemoteRisk
[3] 检测层      ACBlock（上行拦截） · AntiRevert（上报伪装） · Stealth · Prot（反指纹） · AC（D1~D14 自检）
[4] 移动层      SYS._Move（唯一移动核心） + Fly / Speed / Noclip / InfiniteJump / TP(tpStepChain)
[5] 视觉层      ESP / Tracer / HitMark / FreeCam / 光照 / HUD
[6] 战斗层      Gun / RayHook / Combat(死亡登记) / DRCombat
[7] 玩法层      各游戏专用模块（DeadRails / MachineParty / DOORS / FFA / 交易 / 挂机 / 翻译）
[8] 界面层      UI 框架 + Pages（每页只允许"调 setter"，禁止直接改状态）
```
**硬规则**：④ 只有 `SYS._Move` 能创建/销毁角色上的约束实例；⑧ 里任何开关都必须走 `setter`（方便审计接线四点）。

### 阶段划分（每阶段独立可交付、可发版、可回退）
| 阶段 | 内容 | 验收（可自动） |
|---|---|---|
| **P0** | 建"清点 + 接线四点"自动检查脚本（已在做，本次已产出） | 数字基线固化 |
| **P1** | **只搬不改**：把 19040 行按上面 8 层切成 8 个文本区块（仍单文件），每块加统一头注释与边界锚点 | `luau-compile` 0 错误 + `-- 代码部分逐字符不变` 自证 |
| **P2** | 抽"内核层"为独立可注入模块（`SYS.P/T/TT/SetLoop/SafeHook`），其余只改调用 | 同上 + 引用计数不变 |
| **P3** | 统一"开关四点"生成器（一个表声明 = 自动出 T_ 默认/UI/卸载），**删掉手写重复** | 开关数不减、`luau-compile` 0 |
| **P4** | 玩法层按游戏拆成独立 `do` 块 + 统一 `module.Install/Uninstall` 接口 | 同 P3 |
| **P5** | 清"历史实现残留"（按本次清点法逐项裁决，✅ 才动） | 每项给证据 + 用户点头 |

⚠ **P1 之前不改任何一行逻辑**；P2~P5 每阶段单独发版，随时可以叫停。

## 五、需要你定的两件事

1. **走哪条路**：**(A) 分阶段重构**（推荐：P1 起，每阶段可验证可回退）还是 **(B) 一次性全部重写**（我会做，但必须直说：无法验证、大概率一次性搞坏）。
2. 若选 A：**先做 P1（只搬不改）还是先做 P5（先清残留）**？我的建议：**P1**（把结构立起来，后面所有清理才安全）。
